The 30-second version

When an online shop takes an order, several services do work at the same time. Payment and stock reservation can happen in either order, but shipping has to wait for both. If you check this by sorting events by timestamp, you get exactly one order. That order can be wrong, because every machine's clock is slightly off, and it's also arbitrary, because concurrent events have no "real" order.

PORV (Partial-Order Runtime Verification) does something different. From OpenTelemetry data, it builds a graph that contains only the "A must come before B" relations it can actually prove. Then it asks one question: is there at least one ordering that respects this graph and that the developer's state machine (DFA) accepts? There are three possible answers: compatible, incompatible, or inconclusive (used when the evidence is incomplete or the search hits a limit).

The evaluation compares PORV with three simpler baselines. This separates how much causal information helps from how much searching alternative orderings helps. The proposal also says plainly what PORV can't catch (scenario S7).

Prerequisites

Distributed & asynchronous systems

What "asynchronous service interaction" means, and why order gets messy.

Distributed system

A distributed system is a set of processes (programs, usually on different machines) that cooperate by sending messages. They have no shared memory and, importantly, no shared clock. Microservices are one way to build such a system: each service owns one responsibility (orders, payments, stock, shipping) and its own data.

Synchronous vs asynchronous

SynchronousAsynchronous
IdeaCaller waits for the answerCaller continues; work finishes independently later
ExampleHTTP request → wait → responsePublish to a queue (Kafka); or fire several HTTP calls concurrently
OrderingMostly sequential, easy to reason aboutThings overlap; many interleavings possible

Your proposal is careful here (§2.1): the transport doesn't decide it. HTTP can be used concurrently, and a queue doesn't guarantee the business dependencies are right. So PORV doesn't look at the transport. It looks at business events and their dependencies.

The running example: an order

Why is this hard to check? Messages get delayed or retried, services fail partially, and logs end up on different machines with different clocks. Each service only sees its own part.

IN YOUR THESIS

Out of scope: consensus protocols (Raft/Paxos), replicas agreeing on values, and infinite executions (liveness). The focus is dependencies between business work in different services.

Prerequisites

Time, clocks & happened-before

This is the heart of the motivation: timestamps give you one order, while causality only constrains some pairs.

Physical clocks lie (a little)

Every machine has its own clock. Clocks drift, and synchronization (NTP) leaves errors from milliseconds up to much more. The difference between two clocks is called clock skew. If payment's server clock is 200 ms ahead, a payment that really happened after shipping can get an earlier-looking timestamp, or the other way round.

A timestamp is just "what the local clock said". The proposal's key sentence: differences in timestamps are not enough evidence to establish cause–effect across processes.

Lamport's happened-before (1978)

Leslie Lamport defined a relation a → b ("a happened before b"; your proposal writes a ≺ b) using only things we can actually know:

  1. Same process: if a comes before b in the same sequential execution, then a ≺ b.
  2. Messages: sending a message ≺ receiving that same message.
  3. Transitivity: if a ≺ b and b ≺ c, then a ≺ c.

If neither a ≺ b nor b ≺ a, the two are concurrent: nothing connects them, so no order between them is "the true one".

Partial order vs total order

Think of getting dressed: socks before shoes, underwear before trousers, but shirt and socks in any order. That's a partial order: only some pairs are ordered. A total order puts every pair in order, like one line of events.

  • Sorting by timestamps = forcing a total order, and so choosing one interleaving out of many.
  • Happened-before = a (strict) partial order: irreflexive (not a ≺ a), transitive, and so antisymmetric.

"Unordered" vs "concurrent": a subtle point the examiners may test

Your proposal (§2.3) deliberately says tidak terurut (unordered in the observation) rather than konkuren. Here's why. With incomplete telemetry, a missing path between two events might mean they really were concurrent, or it might mean the edge evidence was lost. Not seeing an edge isn't the same as proving concurrency.

SAY

"Kami memakai istilah tidak terurut karena ketiadaan lintasan pada telemetri yang tidak lengkap bisa berarti bukti hilang, bukan pasti konkuren."

Logical clocks: Lamport clocks & vector clocks

  • Lamport clock: one counter per process, incremented on events and on receive (max+1). If a ≺ b then L(a) < L(b), but the converse fails, so it can't detect concurrency.
  • Vector clock (Fidge 1988, Mattern 1989): one counter per process. a ≺ b ⇔ V(a) < V(b) componentwise. It captures causality exactly.

Your proposal doesn't propose a new clock and doesn't assume OTel spans carry vector clocks (they don't). Vector clocks are the conceptual foundation. The edges in PORV come from evidence declared in the observation contract.

Possibly / definitely (Chase & Garg 1998)

Global predicate detection asks whether a property possibly held in some consistent global state, or definitely held in all of them. That's the same flavour as "exists vs for all orderings". Your proposal says it's related but different: PORV checks whether one word is accepted by a DFA, and it doesn't borrow their complexity results as its own. Omer et al. (2026) monitor branching-time temporal specs over partial-order executions; PORV is restricted to finite workflows.

Prerequisites

Graphs, DAGs & topological sort

PORV turns observations into a graph. Here's the vocabulary.

Directed graph and DAG

A directed graph G = (V, D) has vertices V (here: events) and directed edges D (here: "must come before" evidence). A DAG is a directed acyclic graph: you can never follow arrows back to where you started.

  • Reachability: a ≺ b in the poset ⇔ there's a non-empty directed path a ⇝ b. (The proposal: "in a DAG the relation equals reachability through a non-empty directed path.")
  • Transitive closure: add an edge for every reachable pair.
  • Cycle (a before b before a) = contradictory evidence. PORV doesn't "fix" it; the decision becomes inconclusive (scenario S9).

Topological order = linear extension

A topological order (also called linear extension) lists all vertices in one line so that every edge points forward. A DAG can have many of them. In the order example:

  • created → paid → reserved → shipped (a b c d)
  • created → reserved → paid → shipped (a c b d)

With no edges at all, n events have n! linear extensions. That's why you can't just enumerate them for big graphs.

Kahn's algorithm (the "one topological order" baseline)

repeat:
  pick an event with in-degree 0          ← PORV baseline: smallest ID (frozen lexicographic rule)
  output it, remove its outgoing edges
until no events left                       (if some remain → there was a cycle)

Cost O(|V| + |E|). Graph building and cycle checking in PORV are also O(|V_w| + |D_w|). The expensive part is the search, not building the graph.

IN YOUR THESIS

The "one deterministic topological order" baseline uses the same graph and DFA as PORV but tries only one order. Comparing it to PORV isolates the value of searching alternatives.

Prerequisites

Width, antichains, ideals & Dilworth

This is the math behind "the search is polynomial when the width is fixed". Expect at least one question on it.

Chains and antichains

  • Chain: a set of events that are all ordered with each other (a line). Example: created ≺ paid ≺ shipped.
  • Antichain: a set of events where no two are ordered. Example: {paid, reserved}.
  • Width w: the size of the largest antichain, i.e. the most events that can be "in flight at once". Order example: w = 2.

Dilworth's theorem (1950)

The minimum number of chains needed to cover the poset is exactly the width w. So you can always split the events into w lines with lengths n₁ … n_w.

How the proposal computes w: minimum chain cover via bipartite matching on the reachability relation. Make a left and right copy of the vertices and connect uL–vR when u ≺ v. Then min chains = n − |maximum matching|. This is reported as a separate structural analysis.

Order ideals = "what's been processed so far"

An ideal (downset) S is a set of events where, if an event is in S, all its predecessors are too. Every prefix of any topological order is an ideal. So the search state "set of processed events" is always an ideal.

Why this gives the bound

An ideal is determined by "how far along each chain you are": a prefix length 0…nᵢ for each of the w chains. So

|I(G)| ≤ ∏ᵢ (nᵢ + 1) ≤ (n + 1)w

Not every combination is valid (edges between chains rule some out), hence "≤". Multiply by |Q| DFA states for the number of configurations (S, q).

Shape (n = 20)Ideals (roughly)
w = 1 (one chain)21: exactly one order, so search is trivial
w = 4, four chains of 5, no cross edges6⁴ = 1,296 (× |Q| ≤ 16 → ≤ 20,736 configs)
Loose bound (n+1)w, w = 421⁴ = 194,481
w = 20 (no edges at all)2²⁰ ≈ 1,048,576. That's why there's a 10⁶ limit

Also: at any configuration, the events you can pick next form an antichain, so there are at most w candidates per step.

Prerequisites

Finite automata (DFA)

The workflow specification is a small state machine that the developer writes.

Definition

P = (Q, Σ, δ, q₀, F)
  • Q: states ("where are we in the workflow")
  • Σ: alphabet of business symbols (created, paid, reserved, shipped)
  • δ: a partial transition function Q × Σ → Q. If a transition is undefined, that step is rejected
  • q₀: start state; F: accepting states

A word (kata) is a sequence of symbols. The language L(P) is the set of words that lead from q₀ to a state in F. Checking one word takes time linear in its length.

Listing 3.1, explained

name: checkout
correlation: order.id          ← group events by this business ID
initial: new
accepting: [completed]
events:                        ← symbol : OTel business point
  created:  order.created
  paid:     payment.succeeded
  reserved: stock.reserved
  shipped:  shipping.started
transitions:
  - [new, created, opened]
  - [opened, paid, paid_only]
  - [opened, reserved, reserved_only]
  - [paid_only, reserved, ready]
  - [reserved_only, paid, ready]
  - [ready, shipped, completed]

Labelling λ and context events (ε)

λ maps each event to a business symbol. Events that aren't in the model's alphabet (e.g. an internal processing step) get the label ε. They don't change the DFA state, but they stay in the graph so their ordering constraints aren't lost (a ≺ x ≺ b still forces a before b). The mapping is frozen before experiments, and real business events can't be hidden as "context".

Why a DFA and not LTL / Petri nets / BPMN?

  • Workflows here are finite and small. A DFA is the simplest thing that captures "allowed sequences", and developers can write it.
  • Deterministic: given a word, there's exactly one run, so it's cheap to check and pairs naturally with the (S, q) search.
  • LTL is for infinite traces and liveness (out of scope). Petri nets model concurrency inside the model. In PORV, the concurrency lives in the observation (the partial order), and the DFA only says which sequences are allowed.
  • The proposal explicitly says it doesn't develop a new formal language.

Observability & OpenTelemetry

Where the evidence comes from, and why you can't just trust it blindly.

Observability and the three signals

Observability means judging a system's internal state from the data it emits while running. That data is called telemetry.

SignalWhat it isWhy not the main source for PORV
LogsDiscrete text/structured recordsApp-specific format, high volume, no automatic cross-service links
MetricsNumeric aggregates over time (count, latency)Lose request identity and individual event order
TracesThe path of one request through related operationsChosen: they keep per-request structure and cross-service correlation

OpenTelemetry (OTel)

OTel is a vendor-neutral standard: a specification, SDKs (libraries in your code), and a Collector (receives, processes, and exports data). Data travels over OTLP (OpenTelemetry Protocol), which has a JSON encoding. PORV reads exported OTLP JSON.

KEY LIMITATION (you'll say this often)

OTel defines how context and attributes are carried. It does not define the business meaning. That's why the thesis needs an observation contract.

Trace, span, span event, attributes

  • Trace: all spans for one request (shared trace_id).
  • Span: one operation, with span_id, parent_span_id, name, start/end time, attributes, events, links, and status. It has a duration.
  • Span event: a named, timestamped point inside a span. PORV uses these as business points.
  • Attributes: key–value pairs, e.g. order.id = 42, used to group events into a workflow.
// illustrative shape (simplified OTLP JSON)
{ "traceId": "4bf9…", "spanId": "00f0…", "parentSpanId": "a3c2…",
  "name": "charge", "startTimeUnixNano": "...", "endTimeUnixNano": "...",
  "attributes": [{ "key": "order.id", "value": { "stringValue": "42" } }],
  "events": [{ "name": "payment.succeeded", "timeUnixNano": "...",
               "attributes": [{ "key": "porv.predecessors", ... }] }] }

Why a point, not a whole span?

payment.requested (span starts) ≠ payment.succeeded (money actually taken). If you used span start as proof of payment, you could judge the flow wrongly. So the contract records success after the business action has been committed, using a span event or a special span that starts at the success point.

Parent–child, links, context propagation

  • Parent → child: the parent's start comes before the child's start (the child's context is created from it). But the parent's end, or events the parent records later, are not automatically before the child. In async code, a parent can finish before its child does.
  • Links: connect a span to other span contexts (e.g. batch processing). They're generic, so not treated as causal unless the contract explicitly marks them (porv.causal) with a stated direction.
  • Context propagation / W3C Trace Context: the traceparent header carries the trace/span ID across services.
  • Messaging semantic conventions (status: development): producer/consumer spans for queues. Even so, PORV must distinguish one message vs several consumers vs retries. Matching by operation name or timestamp isn't allowed.

Same trace ≠ same order

A business ID like order.id is still needed. One workflow can span several traces, and one trace might touch several orders.

Sampling and incompleteness

Sampling keeps only some traces, and SDKs have recording limits. So "payment not in the export" might mean the payment never happened or it wasn't recorded or exported. A valid OTLP format ≠ all business facts observed. Format validity and semantic completeness are two separate checks.

Kafka in 5 minutes

Needed for the external OTel Demo path (checkout → Kafka → accounting).

  • Producer: sends messages (checkout service).
  • Broker: the Kafka server that stores messages.
  • Topic / partition: a named log, split into partitions. Order is guaranteed only within a partition.
  • Offset: a message's position in a partition (0, 1, 2…).
  • Consumer: reads messages (accounting service).
  • Headers: metadata on a message. The contract carries message ID and predecessor reference here.

sarama.NoResponse: why it matters

The checkout service uses the Go client sarama, configured with NoResponse (acks = 0). The producer doesn't wait for the broker to confirm storage. So "client succeeded" (event c) isn't proof the broker stored the message, and the producer offset isn't reliable either. That's why the study checks broker offset ranges separately and takes the position from the consumer side.

ALSO

"Log call returned" (accounting's event p) doesn't guarantee the log was persisted. The proposal is honest about this: p means "the logging action in this revision finished", not "a database changed".

Runtime verification & conformance checking

Where PORV sits among verification techniques.

The verification spectrum

TechniqueChecksStrength
TestingChosen inputsCheap, incomplete
Model checkingAll behaviours of a modelExhaustive, but on a model, and suffers state explosion
Runtime verification (RV)An actual execution against a specReal behaviour, but only what you observed

Leucker & Schallhart (2009): RV checks observed behaviour against a specification. Online RV checks while the program runs; offline RV checks recorded traces afterwards. Mahé et al. (2022) explicitly do offline RV on collections of local traces.

"IS IT REALLY RUNTIME IF OFFLINE?"

"Istilah runtime merujuk pada sumber bukti yang diperoleh saat aplikasi berjalan; keputusan diberikan setelah ekspor ditutup. Ini sejalan dengan verifikasi runtime offline menurut Leucker & Schallhart serta Mahé dkk."

Three-valued verdicts

RV often uses verdicts like true / false / ? (e.g. LTL₃), because a finite observation sometimes can't decide. PORV's compatible / incompatible / inconclusive follows the same spirit, but "?" here comes from evidence quality or resource limits.

Conformance checking (process mining)

Process mining compares an event log with a process model. Adriansyah et al. (2011) use cost-based alignments with A* search on Petri nets: they count inserted/skipped activities to measure deviation. Their log traces are total orders. PORV keeps the observation as a partial order and asks a yes/no existence question without inserting or deleting business actions.

Decentralised monitoring

Bauer & Falcone (2012) split an LTL formula into local monitors on each component. PORV is centralised, runs after collection, and uses a finite DFA plus evidence gates. Decentralised monitoring is a scope comparison, not something PORV implements.

Prerequisites

Complexity: NP-complete, but polynomial for fixed width

"Isn't this exponential?" Yes, in general. Here's how to answer calmly.

P, NP, NP-hard, NP-complete in plain words

  • P: solvable in polynomial time.
  • NP: a proposed solution (a certificate) can be checked in polynomial time.
  • NP-hard: at least as hard as every NP problem.
  • NP-complete: in NP and NP-hard. No polynomial algorithm is known.

Constrained topological sorting

"Does the DAG have a topological order whose word is in a regular language?" is constrained topological sorting. Amarilli & Paperman (ICALP 2018) proved it's NP-hard even for a fixed language like (ab)*. With an explicit DFA, a candidate order is checkable in polynomial time, so it's in NP, and therefore NP-complete.

BE PRECISE

This doesn't mean every small workflow model is that hard. And the proposal doesn't claim the algorithm is new: memoised search over (S, q) is known conceptually. The contribution is measuring its cost under a declared contract and width profile.

Parameterised view

  • General bound: |Q| · 2ⁿ configurations.
  • With width w: |Q| · (n+1)ʷ, which is polynomial for fixed w, with the exponent depending on w.
  • Per configuration: at most w candidates (an antichain). A simple implementation scans O(n + m), plus set copying and memo management.
  • Therefore width is a controlled experimental factor (w = 1, 2, 4; 8 as a stress test), not just "number of service branches".

What memoisation buys

Different orders can reach the same (S, q). Example: "paid then reserved" and "reserved then paid" both reach S = {created, paid, reserved}, q = ready. Storing visited (S, q) means each pair is explored at most once, so cost depends on the number of configurations, not the (possibly factorial) number of orders.

Metrics & statistics

The evaluation chapter is stats-heavy. Here's each method in plain words.

Confusion matrix (positive = incompatible)

For observation-conformance labels, the positive class is "incompatible with model".

Verifier rejectsVerifier accepts
Truly incompatibleTPFN (missed)
Truly compatibleFP (false alarm)TN
FPR = FP/(FP+TN) · FNR = FN/(FN+TP) · Precision = TP/(TP+FP) · Recall = TP/(TP+FN)

A zero denominator is reported as undefined, never as 0. Inconclusive is outside the binary matrix.

Coverage, abstain & risk

C = (Ncompatible + Nincompatible) / Nall inputs

Why? A checker that always says "I don't know" makes zero errors. Coverage stops that from looking good. Risk = error rate among the inputs that were decided. Lower risk with lower coverage is a trade-off, not a free improvement, which is why there's a risk–coverage plot. Abstains are split into "insufficient evidence" vs "search limit".

Three separate label sets (very important)

LabelQuestionSource (oracle)
Observation conformance (existential)Does an accepted order exist?Brute-force enumeration (small graphs) / constructions with known witness
Application faultDid the app actually break a business rule?Scenario, action logs, independent business facts. Positive = known fault; incompatible = alarm; compatible = no alarm; inconclusive = abstain
Path support (prerequisite)Is there a causal path prerequisite ⇝ action?Independent path oracle

They're never merged. Example: in S7, PORV is correct on the observation label (compatible) but misses the fault on the app label.

Independent units & pseudo-replication

An independent unit is one base graph from a distinct seed, or one app execution from a fresh state. Clock shifts, telemetry loss, and timing repetitions of the same unit stay in one group. Counting them as extra samples would inflate confidence (pseudo-replication). Repeating timing on the same trace adds timing samples, not detection samples.

Bootstrap percentile CI

Resample the independent units (with replacement, within source/scenario strata, keeping method pairs together) 10,000 times with a fixed seed, recompute the statistic each time, and take the 2.5th and 97.5th percentiles → 95% CI. It's used for differences in error rate, coverage, and median paired time difference, and needs no normality assumption.

McNemar exact test

This is for paired binary outcomes: both methods judged the same inputs. Only the discordant pairs matter: b = A right & B wrong, c = A wrong & B right. Under H₀ (equal accuracy), b ~ Binomial(b + c, ½). It's exact because discordant counts can be small. Only pairs where both gave a binary decision are used; the number used and excluded is reported. No discordant pairs → p = 1; no eligible pairs → undefined.

Holm correction

There are 4 comparisons (PORV vs each of 3 baselines + vs prerequisite analysis) × 2 classes (app correct / app faulty) = 8 tests. Sort the p-values from smallest to largest and compare p₍ᵢ₎ with α/(m − i + 1): 0.05/8, 0.05/7, …. Stop at the first failure. This controls family-wise error at 0.05 and is uniformly more powerful than Bonferroni. The family size stays 8 even if some tests are unavailable.

Clopper–Pearson exact interval

This is an exact binomial CI for FPR/FNR, reported with numerator and denominator. It works even with zero errors: 0/30 gives an upper bound ≈ 11.6%. So "0 errors" never means "0% error rate". It's only used for independent Bernoulli observations, not clustered controls.

Timing statistics

Report the median, IQR, and p95 in ms. Core time is measured after parsing/normalization; end-to-end time runs from reading input to serializing the report. There are 5 warm-ups (JIT/cache) and ≥ 30 measured reps. Runs stopped by the limit are censored at the limit. Effects and intervals are the main results; p-values only support interpretation.

The Research · Bab I

The problem & motivation

Slide 2: "Kausalitas membatasi urutan, timestamp memilih satu."

Four sub-problems in the background

  1. Timestamps misrepresent relationships. Clocks differ across services, and sorting forces a single total order on events that are actually concurrent.
  2. Technical observation ≠ business event. The start of a payment span isn't a successful payment, so the point where you record matters.
  3. Evidence can be incomplete. Sampling and loss mean "not observed" isn't the same as "didn't happen". Treating loss as failure creates baseless alarms.
  4. Evaluation must separate causes. Does a better result come from causal information, from searching alternatives, or from evidence quality?

The gap (as stated in Bab I)

What's missing is an approach with a clear observation contract, simple interaction rules, and an evaluation that separates the effect of timestamp ordering from the effect of evidence quality. Partial orders and conformance checking each exist already. The contribution is designing and evaluating workflow conformance checking on OpenTelemetry data for async apps, including the limits of interpreting span relationships and explaining violations.

SAY (motivation in 3 sentences)

"Timestamp memberi satu urutan, padahal kausalitas hanya menuntut sebagian pasangan berurutan. Selain itu, span teknis tidak sama dengan peristiwa bisnis, dan peristiwa yang tidak terekam belum tentu tidak terjadi. Karena itu kami butuh kontrak observasi, pemeriksaan berbasis urutan parsial, dan status tidak dapat disimpulkan."

The Research · §2.5

Core idea: existential compatibility

If you understand this page, you understand the thesis.

compatible(G, P) ⇔ ∃ π ∈ Lin(G) : λ(π) ∈ L(P)

Reading it piece by piece

SymbolMeaning
G = (V, D)Causal graph of one workflow: events V, proven "before" edges D
Lin(G) / TopSort(G)All topological orders (linear extensions) of G
πOne such order
λ(π)Its word: events mapped to business symbols, ε-events dropped
L(P)Words the DFA accepts
∃"At least one". This is the existential part
READ ALOUD (ID)

"Observasi kompatibel dengan model jika ada sedikitnya satu urutan topologis graf yang, setelah dipetakan ke simbol bisnis, diterima oleh DFA."

Why "there exists"?

If two events are unordered, the evidence can't tell us which came first. If some allowed ordering fits the model, then the observation can be explained by the model, and we have no evidence-based grounds to call it a violation. Rejection means no ordering consistent with the evidence fits. That's a strong, defensible claim.

Compatible ≠ correct

THE MOST IMPORTANT CAVEAT

"Kompatibel ⇏ aplikasi benar." Example: payment and shipping are unordered in a complete observation. The order "payment → shipping" is accepted, so the result is compatible. But that doesn't prove payment was a causal predecessor of shipping. The app might have shipped without waiting (scenario S7).

Three possible semantics, compared

SemanticsQuestionStrengthIn thesis?
ExistentialDoes at least one causal order fit the model?Weakest claim, safest rejection (no false alarm from concurrency)Main
UniversalDo all causal orders fit?Stronger: "the app enforces the order". Missing edges cause false alarmsNo (named as stronger alternative)
Prerequisite pathIs there a causal path prerequisite ⇝ dependent action?Stronger for explicit dependenciesSecond analysis, own labels

Closing question on slide 15: "Cukup satu urutan yang diterima, atau semua urutan harus diterima?" Be ready to discuss it (see Question bank).

Asymmetry of the search

  • Accept: you can stop at the first witness.
  • Reject: you must exhaust all reachable configurations.
  • Limit hit: inconclusive, never rejection.

With incomplete evidence

A missing event or edge changes the set of orders and words. So a whole-workflow decision needs the completeness contract Kw. Without it, the status is inconclusive. Compatible only holds for the stated model, observation, and workflow scope. It's not a proof of the whole implementation or of liveness.

The Research · §3.2.2

The observation contract

Contribution #1 (RM1). OTel gives structure; the contract gives meaning.

Three sources of information

  1. Standard OTel info: trace/span IDs, parent–child, links, span events, messaging context. These give structure and correlation, but no business dependencies.
  2. Business instrumentation: workflow ID (order.id) and business points (payment.succeeded). The developer decides their meaning and timing, stored via standard attributes and span events.
  3. Extra causal metadata: local sequence numbers or predecessor references, used when standard context can't express the needed relation.

Completeness is a guarantee of controlled collection, not an automatic property of OTLP.

Normalized event record

Each event has a unique ID, event type, service, trace/span ID, workflow ID, and predecessor references. The timestamp is kept for baselines and explanations, but never used to infer cross-service edges. One business event must not silently become several counted actions.

Events are grouped by order.id. Intermediate events that don't match a rule are kept (they may be on a causal path). References to another order are flagged as an evidence defect, so a prerequisite can't be "satisfied" by another order.

Accepted edge sources (Dw)

✓ Accepted✗ Not accepted
1. Local execution order guaranteed by instrumentation (sequence number / predecessor ref)"Same service" without the same execution sequence (one process handles concurrent work)
2. Parent span start → child span startParent end / later parent events → child
3. Message send → processing, with matching message ID & contextMatching by operation name or timestamp
4. Links / predecessor refs explicitly given causal meaning (porv.causal, direction stated)Generic links without contract direction; timestamps of any kind

PORV-specific attributes

  • porv.predecessors: list of predecessor event IDs in the same workflow. Each means "must appear before me".
  • porv.causal: boolean on a link saying "this link has causal meaning per the contract". Both endpoints and the direction must still be explicit.
  • These are not standard OTel attributes. The serialization format is frozen with the contract before experiments. (The construct-validity section says extra attributes are reported, so "uses OpenTelemetry" doesn't hide the extra instrumentation.)

Input validation

  • Checks: duplicate IDs, correlation values, unresolved references, cycles.
  • Schema-invalid export → input error (reported separately).
  • Cycle → not forced into a partial order; inconclusive until explained.

Completeness flag Kw

Kw is given only to controlled collections where all business points and needed causal references were collected and there's no known loss.

  • Request closing or span end time doesn't prove Kw.
  • Action logs, written on a path separate from telemetry, are reconciled one by one with the export (including events in other trace contexts).
  • If a source is mid-action, logs can't be reconciled, or there's an uncovered failure → no completeness.
  • DFA acceptance is never used as completeness evidence (that would be circular).
  • In fault scenarios, "normal action count" isn't a completeness condition: an intentionally skipped action (S5) differs from a performed-but-lost one (S8).
  • In telemetry-loss tests, Kw is revoked and the loss is recorded.
The Research · §3.2.3

The search algorithm

Contribution #2 (RM2). A memoized search over configurations (S, q). Try the stepper below.

Configurations

  • A configuration is (S, q): S ⊆ Vw = processed events (always an ideal), q ∈ Q = DFA state. Start at (∅, q₀).
  • Event v ∉ S may be picked only if all its direct predecessors are in S.
  • If λ(v) = ε, the state stays; otherwise δ(q, λ(v)) must exist. Step → (S ∪ {v}, q′).
  • S = Vw and q ∈ F → stop with a witness → compatible.
  • All reachable configurations explored, no witness → incompatible.
  • Memo on (S, q): never explore the same pair twice. Candidates are ordered by ID, so the witness is deterministic.
  • Limits (10 s core time or 10⁶ configurations, whichever comes first) → inconclusive, not rejection.
search(G, P):
  memo ← {(∅, q0)};  stack ← [(∅, q0, [])]
  while stack not empty:
    if time > 10s or |memo| > 10^6: return INCONCLUSIVE
    (S, q, path) ← pop(stack)
    if S = V:
      if q ∈ F: return COMPATIBLE(witness = path)
      continue
    for v in ready(S) sorted by id:          # all preds of v in S
      q' ← q if λ(v) = ε else δ(q, λ(v))
      if q' undefined: continue               # DFA forbids this step
      if (S∪{v}, q') ∉ memo:
        memo.add((S∪{v}, q')); push((S∪{v}, q', path+[v]))
  return INCOMPATIBLE                         # exhaustive, no witness

Cost summary

  • Graph build + cycle check: O(|Vw| + |Dw|).
  • Configurations ≤ |Q| · ∏(nᵢ+1) ≤ |Q|(n+1)w; general |Q|·2ⁿ.
  • Time ≈ |Q|(n+1)w × polynomial factor (scanning, set copying, memo). Memory also counts the size of each configuration's representation.
  • The general problem is NP-complete (Amarilli & Paperman). Polynomial for fixed w.
  • Width is computed separately (bipartite matching) and reported as structure analysis if not needed by the core.
  • Scale plots show time, #configurations, and stop proportion vs n for each w, with the model and acceptance type held constant.
  • Many small graphs ≠ one big workflow with many order choices. The proposal never treats these as equivalent.

All strategies get the same events, symbol mapping, DFA, and evidence gates. Only the ordering strategy differs, which makes it a controlled comparison.

What each comparison isolates

  • Timestamp vs one topological order → value of causal information.
  • One topological order vs PORV → value of exploring alternatives.

Raw timestamp

Sort ascending by physical time (ID breaks ties), run the one resulting word, and don't search further if it's rejected. Missing timestamp → inconclusive. If the timestamp order contradicts a causal edge, that's flagged in the report but not fixed using the graph (a "graph-corrected timestamp" would be a different baseline). It's explicitly not "the best available verifier", just a controlled contrast.

Timestamp with clock-error bound

Each event becomes an interval Ie = [te − εe, te + εe], where εe is the source clock's absolute error bound (incl. resolution), frozen before measurement. e is surely before f only if sup Ie < inf If. The DFA runs only if the intervals determine one total order over the model's events; otherwise → inconclusive. Expect lower coverage on overlapping intervals, analysed with risk–coverage. Sensitivity uses k ∈ {0, ½, 1, 2} × ε. Shifts beyond the bound are reported as clock-assumption violations.

One deterministic topological order

Kahn with smallest ID first, no timestamps, same graph and DFA. It runs one order and doesn't retry after a rejection.

Two useful facts (great for answering "when does it matter?")

  1. If the timestamp order is a valid topological order and is accepted, PORV must also accept. So "baseline accepts but PORV rejects" can only happen if timestamps contradict causality (or there's an implementation bug).
  2. If the DFA's verdict doesn't change when you swap any two adjacent unordered events, all topological orders give the same verdict. In that class, one order is enough and search adds nothing. (Intuition: Mazurkiewicz trace theory, where the language is closed under commuting independent events.) The corpus therefore must include graphs with both accepted and rejected orders.

The Research · §3.2.4

Second analysis: causal prerequisite paths

Backup slide 16. It complements the existential check where it's blind (S7).

  • Question: is there a causal path from the prerequisite (e.g. payment.succeeded) to the dependent action (shipping.started)?
  • Profile: explicit dependency rules only, no repetition. Rule type, dependent action, business-ID matching, and repetition policy are frozen before the corpus.
  • Outputs: prerequisite supported / not supported / inconclusive. Complete evidence + no path → not supported. Incomplete → inconclusive (same gate).
  • Non-vacuous: existence and count of required actions are stated separately, so a missing dependent action doesn't make the check pass trivially.
  • No path ≠ automatically "done too early". Calling it an enforcement violation needs a business requirement about causality and a contract that records it. App-fault labels still come from independent facts.
  • It's not derived from an arbitrary DFA, not equal to universal semantics, and validated against its own path oracle (not the existential label).
  • If used as an alarm, TP/FP/FN/TN are recomputed against business facts. An alarm on a correct app counts as FP on the app label even if it's "right" on the path label.
  • It reuses the preliminary prototype, aligned with the new evidence gates.
The Research · §3.2.5

Explaining (in)compatibility

  • Accept → one witness order.
  • Reject → model, workflow ID, relevant events, ordering constraints, and a summary of the exhaustive search.
  • One failing order is not a sufficient counterexample under existential semantics, because another order might be accepted. The exploration over the full graph is what justifies the conclusion; the event slice only helps explain it.
  • Simple cases (shipping known to precede payment) show the path and the conflicting transition. If a correct summary isn't available → report the whole workflow graph.
  • No claim of a minimal counterexample. No user study (both out of scope).
Rslice = nslice / nworkflow

Size = number of unique event IDs shown, relative to the violating workflow (not the whole corpus). Serialized bytes are also recorded. A small ratio doesn't prove the explanation is easy to understand; correctness is checked first.

Evaluation design

Three corpora, three kinds of evidence

Observation conformance, application faults, and path support are reported separately.

Variables

  • Independent variable: checking strategy (PORV, one topo order, raw timestamp, interval timestamp). Prerequisite analysis runs separately.
  • Factors: scenario type, #events n, poset width w, clock skew, evidence quality.
  • Held constant per series: DFA size, edge density, rules, normalized input, machine, process conditions.
  • Corpus split by purpose: small-graph suite (validation), paired cases (isolate causal info vs search), controlled executions (app faults), external integration. Search cases include models that accept all swaps and models that accept only some. For w = 1 the "mixed" class is marked not applicable.

Profile & sampling

  • n = 4, 8, 12, 16, 20; w = 1, 2, 4 (w ≤ n); |Q| = 2–16; w = 8 stress. Compare sizes at fixed width and widths at fixed size.
  • ≥ 30 independent base units per selected cell; numbers frozen before generation; all scheduled samples run, with no stopping based on p-values.
  • Clock shifts 0, ±100 ms, ±1 s, ±5 min. Loss via fixed-seed removal of relevant events.
  • Loads 100/500 events (optional stress), 1,000/5,000 (optional extension). Two load shapes: many independent workflows vs one growing workflow.

Data collection

  • Fresh app state per run; store business-fact records + treatment config; collect telemetry; validate evidence quality.
  • The same normalized input goes to all strategies; time metadata and error bounds are used only by the timestamp baselines.
  • Checker execution order is randomized/balanced (load & cache effects).
  • Core time (after parsing) vs end-to-end time; 5 warm-ups, ≥ 30 reps; startup cost separated.
  • Failed runs = experiment failure, not a checker decision. Settings changed after calibration → new corpus/manifest version.

Success criteria (prototype acceptance)

  1. 100% oracle agreement on the complete small-graph suite, no abstain (accept, reject, many orders with one witness, branching workflows).
  2. All known-loss / broken-ref / cycle cases → inconclusive; format errors → input error; all limit-stop tests → inconclusive.
  3. On 100% of pairs where only timestamps or export order change, the PORV decision and canonical explanation are identical (also for the topo baseline and prerequisite analysis; timestamp baselines may change).
  4. All three baselines are complete and tested against their own definitions (incl. the deterministic order failing when an alternative is accepted, and inconclusive on ambiguous intervals). The prerequisite analysis is tested against the path oracle.
  5. At least one real SDK export processed from OTLP JSON to decision + explanation. One external integration path with revision, contract, model, independent labels, and inspectable patches. Business-fault evaluation is mandatory on the controlled app.

Operational targets (design choices, frozen)

On complete observations in the main profile: ≥ 95% decided, limits 10 s / 10⁶ configs, ≤ 5% stopped. These suit offline small workflows. They're not measured values and not conditions for "beating" baselines. Missed targets are still results and are reported.

Manifest & freezing

A pre-calibration manifest records targets, generator, size/width/model combos, sample counts, identity rules, clock assumptions, abstain handling, stats plan, and timing procedure. Pilot/calibration seeds are separate from evaluation seeds. Calibration only checks implementation, oracle, cell feasibility, and measurement tools. Revisions after freezing → a new protocol version, with old results kept. This is close to a pre-registration-style design and protects against tuning to the results.

Deep dive: S7, the honest limitation

  • Setup: in the app variant, prerequisite enforcement is disabled and shipping runs before payment, proven by controlled action logs.
  • PORV: the graph has payment and shipping unordered, so the order "payment → shipping" exists and is accepted → compatible. On the observation label that's correct. On the application label it's a missed fault (FN).

  • Interval variant: catches it if the intervals are surely separated; abstains if they overlap.
  • Prerequisite analysis: no path payment ⇝ shipping → "not supported". It complements the interpretation.
  • Why not run the variant on one process? Recorded local order would add an edge, turning it into S4.

BE HONEST ABOUT WHAT THIS PATH PROVES

Both topological orders are accepted, so this path shows no search benefit over one topological order. It evaluates SDK integration, dependency reconstruction, collection completeness, and clock sensitivity. Order contradictions on modified graphs are reported as synthetic controls. External business-fault cases need independent requirements and proven faulty executions.

Bounded closure procedure (Appendix A.2)

  1. Checkout and accounting write action logs separate from the telemetry SDK, fsynced to disk (a write failure fails the source). Accounting logs a "processing" phase before and a "done" phase after.
  2. After a successful checkout response, both sources are frozen. If accounting is frozen mid-processing → inconclusive (the action may have happened before its record).
  3. Broker offset range is checked against accounting's position. Fresh profile: exactly one message at offset 0.
  4. Telemetry is allowed to reach the collector, then the collector is stopped normally to close the export (waiting alone proves nothing). Each event is reconciled one by one, and dropped counts are checked.

Profile: fresh broker, 1 partition, 1 successful order, 1 message, no retries/restarts. Kw is given only if reconciliation succeeds, no failure/restart occurred, accounting is outside an action, and the collector stopped normally.

The Research · §3.1.1 & §3.4.4

Scope, limitations & threats to validity

Scope (8 points)

  1. Controlled app, synthetic graphs, one OSS workflow (OTel Demo 2.0.2). The external path covers integration only.
  2. DFA per workflow, existential semantics; the prerequisite analysis only for explicit dependencies. No new formal language, no consensus, no unbounded liveness.
  3. Offline checking. "Runtime" = evidence from running apps. No streaming, no automatic intervention.
  4. Input: normalized OTLP JSON. No binary formats, no every-backend support, no automatic instrumentation of whole apps.
  5. Event identity, workflow identity, and dependency direction are defined in the contract. Standard traces without business info aren't enough.
  6. Not every span link = happened-before.
  7. Mandatory baselines: raw timestamp, timestamp ± bound, one deterministic topo order.
  8. Explanations = deterministic relevant-event slices. No global minimality, no user study.

Three risks (slide 13)

RiskMitigation
Causal edges wrong or missingContract frozen before data; independent action reconciliation; defective evidence → inconclusive
Search blows upWidth controlled; #configurations measured; limits; every target miss reported as is
Circular evaluationGraph oracle and business facts made without PORV; coverage always shown with accuracy

Threats to validity

  • Internal: labels from the verifier itself would be circular → independent oracles. The existential label favours PORV by definition → separate app & path labels. Non-atomicity between action, log write, and telemetry → freezing + reconciliation; no claims about crash recovery or production. Synchronous log writes affect timing → same instrumentation profile in pairs. Machine load, JIT, cache, and run order are controlled/recorded.
  • Construct: accepting one order ≠ certainty about real behaviour. Summary size ≠ usefulness. Extra OTLP attributes are reported as an app contract.
  • External: one 3-event external contract; search benefit only from controlled + synthetic data; small models; transport, retry, fan-out, batching differences reported.
  • Reliability/reproducibility: rules, raw input, normalization, labels, seeds, configs, per-run results stored; versions locked; determinism tests; raw timing data published.

Related Work · Bab II §2.6–2.7

How is this different from other research?

Rule: for every paper, be able to say "they do X, we do Y, and we're not claiming Z". Never claim novelty for the idea of checking multiple orderings.

Where the thesis sits

Between process checking from tracing (Sakai, Sun) and trace validation against formal specs (Ellsberg, TraceLink, Weil-Kennedy). Three aspects get attention: sufficiency of evidence to build causal edges, distinguishing violation from incompleteness, and cost + explanation size.

So what IS the contribution?

HONEST ANSWER
  1. Integration: existential partial-order checking + an OpenTelemetry business observation contract (what counts as an event, an edge, and "complete").
  2. Three-valued handling of evidence: violation vs unknown, with a completeness gate and explicit tests (S5 vs S8).
  3. Evaluation design that isolates effects: three baselines, independent oracles, three label sets, risk–coverage, pre-frozen manifest.
  4. Honest boundary map: S7 and the fact that the external path shows no search benefit.
  5. Artifacts: prototype, labelled corpus, reproducible protocol, cost/width analysis.
